# 과제 목표 항목별 답변

카페 주문 관리 DB(`category`, `customer`, `menu`, `orders`, `order_item`)를 직접 만들어 보면서 정리한 답변이다.
예시는 모두 이 과제의 실제 테이블, 데이터, 쿼리 결과를 바탕으로 한다.

---

## 1. 데이터베이스가 엑셀과 뭐가 다른지, 왜 테이블로 나눠 저장하는지

### 엑셀처럼 한 시트에 저장하면

| 주문일 | 고객명 | 전화번호 | 메뉴 | 카테고리 | 가격 | 수량 |
|---|---|---|---|---|---|---|
| 2026-08-03 | 김민준 | 010-1111-0001 | 아메리카노 | 커피 | 4500 | 1 |
| 2026-08-03 | 김민준 | 010-1111-0001 | 크루아상 | 베이커리 | 3800 | 1 |
| 2026-08-12 | 김민준 | 010-1111-0001 | 아메리카노 | 커피 | 4500 | 1 |

이렇게 저장하면 다음 문제가 생긴다.

- **중복 저장**: 김민준의 전화번호가 주문 줄마다 반복된다. 이 과제 데이터로 치면 38줄에 고객 정보가 반복된다.
- **수정 이상**: 전화번호가 바뀌면 그 고객의 모든 줄을 고쳐야 한다. 한 줄이라도 빠뜨리면 같은 사람의 번호가 두 개가 된다.
- **삽입 이상**: 아직 주문하지 않은 고객(한예준, 오하은)이나 아직 안 팔린 메뉴(밤라떼)는 주문 줄이 없어서 저장할 곳이 없다.
- **삭제 이상**: 어떤 고객의 유일한 주문을 지우면 그 고객 정보까지 함께 사라진다.
- **규칙이 없음**: 가격 칸에 `-500`이나 `"오천원"`을 써도 막을 방법이 없다.

### DB는 이렇게 해결한다

- **한 가지 정보는 한 곳에만 저장한다.** 고객은 `customer`, 메뉴는 `menu`, 주문은 `orders`에 따로 저장한다.
- 다른 테이블의 정보가 필요하면 **번호(FK)만 저장**해 두고, 조회할 때 연결(JOIN)한다.
  - 예) `orders`에는 고객 이름 대신 `customer_id = 1`만 저장한다.
  - 전화번호가 바뀌어도 `customer` 테이블에서 1행만 고치면 모든 주문에 반영된다.
- **제약조건으로 규칙을 강제한다.**
  - `CHECK (price > 0)`: 음수 가격을 막는다.
  - `phone UNIQUE`: 같은 번호로 중복 가입하는 것을 막는다.
  - FK: 없는 고객의 주문을 막는다.
- 여러 사람이 동시에 사용하고 데이터가 많아져도 SQL 한 줄로 검색, 정렬, 집계를 할 수 있다.

> **정리**: 엑셀은 "보기 좋은 표"이고, DB는 "관계와 규칙을 가진 데이터 저장소"이다.
> 차이는 데이터의 양이 아니라 **관계를 표현하고 규칙을 지키게 할 수 있느냐**이다.

## 2. PK / FK가 무엇이고, 1:N 관계가 데이터를 어떻게 연결하는지

### PK (Primary Key, 기본 키)

- 테이블에서 **행 하나를 구별하는 값**이다. NULL일 수 없고, 같은 값이 두 번 나올 수 없다.
- 예) `customer.id`
  - 동명이인 "김민준"이 두 명 있어도 `id`가 다르면 서로 다른 고객이다.

### FK (Foreign Key, 외래 키)

- **다른 테이블의 PK를 가리키는 값**이다. 가리키는 행이 실제로 있어야만 저장된다.
- 예) `orders.customer_id`는 `customer.id`를 가리킨다.
  - `customer_id = 999`처럼 없는 고객 번호를 넣으면 `FOREIGN KEY constraint failed` 에러가 난다. (`bonus.sql` B03)

### 1:N 관계

"부모 하나에 자식이 여러 개 연결되는 관계"이다. **N 쪽(자식) 테이블이 FK를 가진다.**

| 1 (부모) | N (자식) | 연결하는 FK | 의미 |
|---|---|---|---|
| customer | orders | `orders.customer_id` | 고객 1명이 주문을 여러 번 한다 |
| category | menu | `menu.category_id` | 카테고리 1개에 메뉴가 여러 개 있다 |
| orders | order_item | `order_item.order_id` | 주문 1건에 메뉴가 여러 개 담긴다 |
| menu | order_item | `order_item.menu_id` | 메뉴 1개가 여러 주문에 등장한다 |

**연결 예시**

```
customer (id=1, 김민준)
   ├─ orders id=1  (customer_id=1)  ─┬─ order_item: 아메리카노 1잔
   │                                 └─ order_item: 크루아상 1개
   ├─ orders id=3  (customer_id=1)  ─── order_item: 아메리카노 1잔
   ├─ orders id=9  (customer_id=1)  ...
   └─ orders id=16 (customer_id=1)  ...
```

- 왜 FK를 N 쪽에 두는가?
  - 1 쪽(`customer`)에 주문 번호를 넣으려면 `order1`, `order2`, ... 칸이 끝없이 필요하다.
  - 반대로 N 쪽(`orders`)은 각 주문마다 "나는 몇 번 고객의 주문"이라는 값 **하나만** 가지면 된다.
- **N:M 관계**: 주문과 메뉴는 서로 여러 개씩 연결된다. 이런 관계는 중간 테이블 `order_item`을 두어 **1:N 두 개로 나눠** 표현한다.

## 3. SELECT / INSERT / UPDATE / DELETE를 언제 쓰는지

| 명령 | 언제 쓰나 | 이 과제의 예 |
|---|---|---|
| **SELECT** | 데이터를 **조회**할 때. 데이터는 바뀌지 않는다. | 판매 중인 비싼 메뉴 TOP 5 (Q01) |
| **INSERT** | 새 데이터를 **추가**할 때 | 고객 가입, 새 주문 접수 (`data.sql`) |
| **UPDATE** | 이미 있는 데이터의 값을 **바꿀** 때 | 누적 결제 3만 원 이상 고객을 GOLD로 승급 (Q16) |
| **DELETE** | 데이터를 **지울** 때 | 취소된 주문 삭제 (Q17) |

### 사용할 때 주의할 점

- **UPDATE / DELETE에서 WHERE를 빼면 테이블의 모든 행이 바뀌거나 지워진다.**
  - 그래서 같은 WHERE 조건으로 SELECT를 먼저 실행해 대상 행을 확인한 뒤 실행한다.
  - Q16과 Q17은 "변경 전 SELECT → 변경 → 변경 후 SELECT" 순서로 작성했다.
- **INSERT 순서**: 부모 테이블부터 넣는다.
  - 예) `category` → `customer` → `menu` → `orders` → `order_item`
- **DELETE 순서**: 넣을 때와 반대로 자식부터 지운다.
  - 단, `ON DELETE CASCADE`를 걸어 둔 관계는 부모를 지우면 자식도 자동으로 지워진다.
  - 예) Q17에서 취소 주문 2건을 지우자 주문 상세가 38행에서 36행으로 줄었다.
- **삭제 대신 상태 변경**: 메뉴는 지우면 과거 판매 기록까지 의미를 잃는다. 그래서 판매를 멈출 때는 DELETE 대신 `UPDATE menu SET is_available = 0`으로 상태만 바꾼다.

## 4. JOIN과 GROUP BY로 연결된 데이터를 한 번에 뽑는 방법

### JOIN: 나눠 저장한 테이블을 다시 이어 붙인다

`FK = PK` 조건으로 짝을 맞춰 옆으로 붙인다.

```sql
SELECT o.id, cu.name, m.name, oi.quantity
FROM orders o
INNER JOIN customer   cu ON cu.id       = o.customer_id   -- 누가
INNER JOIN order_item oi ON oi.order_id = o.id            -- 무엇을 몇 개
INNER JOIN menu       m  ON m.id        = oi.menu_id;     -- 메뉴 이름
```

| 종류 | 결과에 남는 행 | 이 과제의 예 |
|---|---|---|
| **INNER JOIN** | 양쪽 모두에 짝이 있는 행만 | 10월 주문 상세 내역 (Q06) |
| **LEFT JOIN** | 왼쪽 테이블의 행은 짝이 없어도 모두 남는다. 짝이 없으면 오른쪽 값이 NULL | 한 번도 안 팔린 메뉴 (Q08) |

- Q08은 `menu LEFT JOIN order_item` 후 `WHERE oi.id IS NULL`로 짝이 없는 메뉴(밤라떼)만 고른다.
  - 같은 쿼리를 INNER JOIN으로 바꾸면 짝 없는 메뉴가 처음부터 빠져서 결과가 0행이 된다.

### GROUP BY: 같은 값끼리 묶어서 집계한다

```sql
SELECT cu.name, COUNT(DISTINCT o.id) AS 주문횟수, SUM(oi.quantity * oi.unit_price) AS 총결제액
FROM customer cu
JOIN orders o      ON o.customer_id = cu.id
JOIN order_item oi ON oi.order_id   = o.id
WHERE o.status <> 'CANCELED'      -- 묶기 "전" 행 필터
GROUP BY cu.id, cu.name           -- 고객별로 묶기
HAVING SUM(oi.quantity * oi.unit_price) >= 30000   -- 묶은 "후" 그룹 필터
ORDER BY 총결제액 DESC;
```

### 이해한 핵심

- **JOIN하면 행이 늘어난다.**
  - 주문 1건에 메뉴가 2개면 2행이 된다.
  - 그래서 주문 횟수를 셀 때는 `COUNT(DISTINCT o.id)`를 써야 정확하다 (Q10).
- **WHERE와 HAVING의 차이**
  - WHERE는 묶기 **전**에 개별 행을 거른다.
  - HAVING은 묶은 **후**에 그룹을 거른다. `SUM(...) >= 30000`처럼 집계 결과에 대한 조건은 HAVING에만 쓸 수 있다.
- **"평균의 기준"을 정확히 정한다.**
  - 주문당 평균 금액(객단가)은 먼저 주문별 합계를 만들고, 그 값을 월별로 다시 평균 내는 두 단계로 구한다 (Q12).

## 5. 실무에서 흔한 요구(검색 / 정렬 / 집계 / 랭킹)를 SQL로 푸는 방법

요구사항을 SQL 구문으로 바꾸는 습관이 핵심이다.

| 요구 유형 | 사용하는 SQL | 이 과제의 예 |
|---|---|---|
| **검색** | `WHERE`, `LIKE '%키워드%'`, 범위 비교 (`>=`) | '라떼'가 들어간 메뉴 (Q04), 최근 7일 주문 (Q03) |
| **정렬** | `ORDER BY 컬럼 [ASC/DESC]`, 동점일 때를 위한 두 번째 정렬 기준 | 가입일 순 GOLD 고객 (Q02) |
| **집계** | `GROUP BY` + `COUNT` / `SUM` / `AVG` | 카테고리별 메뉴 수·평균 가격 (Q09), 월별 매출 (Q12) |
| **랭킹 / TOP N** | `GROUP BY` → `ORDER BY 집계값 DESC` → `LIMIT N` | 많이 팔린 메뉴 TOP 5 (Q11), 고객별 결제액 순위 (Q10) |
| **없는 것 찾기** | `LEFT JOIN ... IS NULL` 또는 `NOT IN (서브쿼리)` | 안 팔린 메뉴 (Q08), 주문 없는 고객 (Q13) |
| **기준과 비교** | 스칼라 서브쿼리 | 평균 가격보다 비싼 메뉴 (Q14) |
| **추이 / 비중** | 윈도우 함수 `LAG`, 전체 합계 대비 비율 | 전월 대비 매출 증감 (B07), 카테고리 매출 비중 (B08) |

### 요구사항을 SQL로 바꾸는 순서

질문 예시: "취소를 빼고, 많이 팔린 메뉴 5개를 보여줘"

1. **어떤 테이블이 필요한가?** → `order_item`(수량), `menu`(이름), `orders`(취소 여부) → JOIN
2. **어떤 행을 빼야 하나?** → 취소 주문 → `WHERE o.status <> 'CANCELED'`
3. **무엇을 기준으로 묶나?** → 메뉴별 → `GROUP BY m.id`
4. **무엇을 계산하나?** → 판매 수량 → `SUM(oi.quantity)`
5. **어떻게 보여주나?** → 많이 팔린 순으로 5개 → `ORDER BY ... DESC LIMIT 5`

주의할 점: 결과가 매번 같게 나오도록 동점일 때의 정렬 기준도 함께 적는다. 예) `ORDER BY price DESC, id`

## 6. 인덱스가 왜 필요하고, 어떤 컬럼에 적용하면 좋은지

### 왜 필요한가

- 인덱스가 없으면 `WHERE customer_id = 1`을 찾을 때 테이블의 **모든 행을 처음부터 끝까지 확인**한다 (Full Scan).
- 인덱스는 책 뒤의 "찾아보기"처럼 **컬럼 값을 정렬해 두고 행 위치를 기록한 자료구조**(B-Tree)이다. 필요한 행으로 바로 찾아간다.
- 데이터가 20행일 때는 차이가 없지만, 100만 행이면 큰 차이가 난다.

### 이 과제에서 확인한 것 (Q15)

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
CREATE INDEX idx_orders_ordered_at  ON orders (ordered_at);

EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer_id = 1;
-- 결과: SEARCH orders USING INDEX idx_orders_customer_id (customer_id=?)
```

실행 계획이 전체 탐색(`SCAN`)이 아니라 인덱스를 사용한 탐색(`SEARCH ... USING INDEX`)으로 나오는 것을 확인했다.

### 어떤 컬럼에 거는가

| 인덱스를 거는 것이 좋은 컬럼 | 이유 / 예 |
|---|---|
| **WHERE 조건에 자주 쓰이는 컬럼** | `orders.ordered_at` (기간 검색) |
| **JOIN에 쓰이는 FK 컬럼** | `orders.customer_id`, `order_item.menu_id`. PK와 달리 FK에는 인덱스가 자동으로 생기지 않는다. |
| **ORDER BY에 자주 쓰이는 컬럼** | 최신 주문 순 정렬 (`ordered_at`) |
| **값의 종류가 다양한 컬럼** | 전화번호, 날짜처럼 값으로 행이 잘 좁혀지는 컬럼 |

| 인덱스가 효과 없거나 손해인 경우 | 이유 |
|---|---|
| 값의 종류가 적은 컬럼 | `is_available`(0/1), `status`(3종류)는 걸러지는 행이 적어서 효과가 작다. |
| 데이터가 매우 적은 테이블 | 그냥 전체를 읽는 편이 더 빠르다. |
| 쓰기(INSERT/UPDATE)가 매우 잦은 테이블 | 쓸 때마다 인덱스도 같이 고쳐야 해서 느려진다. |
| 이미 인덱스가 있는 컬럼 | PK와 UNIQUE 컬럼은 DB가 자동으로 인덱스를 만든다. |

> **정리**: 인덱스는 **읽기 속도를 위해 쓰기 비용과 저장 공간을 지불하는 것**이다.
> 그래서 "자주 찾는 컬럼"에만 골라서 건다.
