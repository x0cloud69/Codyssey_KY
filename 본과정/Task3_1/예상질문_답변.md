## 항목 2. 모듈 분리와 책임 경계

### Q2-1. 코드가 3개 이상 모듈로 분리되어 있고, 각 모듈의 책임을 "어떻게" 나눴는지 설명할 수 있는가?

**A.** 7개 모듈을 **"바뀌는 이유"가 서로 다른 단위**로 잘랐습니다. 기준은 계층(입출력 / 업무규칙 / 저장 / 데이터)입니다.

| 모듈 | 책임 | 이 모듈이 **하지 않는** 일 |
| --- | --- | --- |
| `cli.py` (216줄) | argparse 명령 해석, 대화형 입력, 화면 출력 | 파일 읽기·쓰기, 합계 계산 |
| `service.py` (170줄) | 업무 규칙 조립 — 카테고리 검증, 월별 집계, 예산 계산, CSV 변환 | JSONL 물리 포맷을 모름 |
| `repository.py` (159줄) | JSONL 파일 I/O, 스트리밍, id 채번, 원자적 재작성 | 사용자 입력·출력 형식을 모름 |
| `models.py` (43줄) | `Transaction` 구조 정의 + 자체 검증 | 저장 위치·명령어를 모름 |
| `decorators.py` (62줄) | 로그·시간측정·예외처리 공통 관심사 | 특정 명령의 업무 규칙 없음 |
| `config.py` (8줄) | 경로·허용 타입 상수 | 실행 중 바뀌는 데이터 없음 |
| `__main__.py` (12줄) | `python -m budget_app` 진입점 | 파싱·저장·계산 안 함 |

**의존 방향이 한 방향(단방향)** 이라는 게 핵심입니다.

`cli → service → repository → models → config`

역방향 import가 하나도 없습니다. 그래서 `repository.py`는 CLI를 몰라도 되고, CLI를 나중에 웹 화면으로 바꿔도 `service`·`repository`는 그대로 재사용됩니다.

**검증 방법**: "출력 문구를 바꾸려면 어디를 여나?" → `cli.py`만. "저장 파일명을 바꾸려면?" → `config.py`만. 한 가지 변경이 한 파일로 끝나면 경계가 제대로 잡힌 겁니다.

### Q2-2. 최소 2개 이상의 클래스에 부여한 책임 경계를 "어떻게" 정했는지 설명할 수 있는가?

**A.** 클래스는 4개이며, **저장소 3개는 "파일 1개당 클래스 1개"**, **서비스 1개는 "여러 저장소를 걸치는 규칙"** 기준으로 갈랐습니다.

**1) `TransactionRepository` (repository.py:10)** — `transactions.jsonl` 하나만 담당

- `add()` append 저장 / `stream()` 한 건씩 읽기 / `next_id()` 채번 / `update()`·`delete()` 원자적 재작성
- **경계 규칙**: "이 클래스는 거래 파일 밖의 것을 절대 모른다." 그래서 카테고리가 유효한지 여부를 여기서 검사하지 않습니다.

**2) `CategoryStore` (repository.py:89)** — `categories.jsonl` 담당

- `list_all()` / `exists()` / `add()` / `remove()`
- 생성자에서 파일이 비어 있으면 기본 5종을 자동 시드합니다(repository.py:94-96). "빈 파일 상태" 처리를 호출자가 매번 신경 쓰지 않도록 클래스 안으로 넣은 것입니다.

**3) `BudgetStore` (repository.py:133)** — `budgets.jsonl` 담당

- 같은 달을 다시 set 하면 덮어쓰는 규칙(`_load()` → dict → 전체 재작성, repository.py:149-156)이 이 클래스 안에 갇혀 있습니다.

**4) `BudgetService` (service.py:7)** — **여러 저장소에 걸친 규칙만** 담당

- 대표 예: `add_transaction()`은 저장 전에 `cat_store.exists(category)`를 먼저 확인합니다(service.py:15-19).
- **이 검사를 왜 `Transaction` 모델이 아니라 서비스에 뒀나?** 모델은 "category가 빈 문자열이 아닐 것"까지만 압니다(models.py:25). "등록된 카테고리인가"는 **다른 파일을 읽어야 알 수 있는 사실**이라 모델의 책임 범위를 넘습니다. 두 저장소를 동시에 아는 유일한 계층이 서비스라서 서비스에 뒀습니다.

**한 줄 정리**: **혼자 아는 사실 → 모델 / 파일 하나 안의 사실 → 저장소 / 파일을 넘나드는 사실 → 서비스.**

### Q2-3. 파일 기반 update/delete를 "어떻게" 안전하게 처리했는지 설명할 수 있는가?

**A.** **임시 파일에 전부 쓴 뒤 `os.replace()`로 통째 교체**하는 원자적(atomic) 방식입니다. 원본을 직접 고치지 않습니다.

`repository.py:48-53` `_rewrite()`:

```python
tmp_path = self.path.with_suffix(self.path.suffix + ".tmp")   # transactions.jsonl.tmp
with open(tmp_path, "w", encoding="utf-8") as f:
    for tx in transaction:
        f.write(json.dumps(tx.to_dict(), ensure_ascii=False) + "\n")
os.replace(tmp_path, self.path)     # 마지막 한 방에 교체
```

**왜 이 방식인가 — 대안과 비교**

- ❌ 원본을 `"w"`로 열고 다시 쓰기: 여는 순간 파일이 0바이트가 됩니다. 쓰는 도중 죽으면 **전 데이터 소실**.
- ❌ 줄 단위 부분 수정(seek): JSONL은 줄 길이가 가변이라 금액이 `15000 → 200000`으로 길어지면 뒤 데이터를 밀어야 합니다. 사실상 불가능.
- ✅ tmp + `os.replace()`: 쓰다가 중단되면 손상되는 건 **tmp 파일뿐**, 원본은 무사합니다. `os.replace()`는 OS가 보장하는 원자적 rename이라 **중간 상태가 외부에 보이지 않습니다**. (덮어쓰기까지 지원해서 Windows/Linux 모두 동작합니다. `os.rename`은 Windows에서 기존 파일이 있으면 실패합니다.)

**"없는 id" 처리도 쓰기 전에 판정합니다** — 파일을 건드리기 전에 먼저 확인하고, 대상이 없으면 아예 쓰지 않고 `False`를 반환합니다.

- delete(repository.py:55-61): 남은 개수가 원래 개수와 같으면 → 지울 게 없다 → `_rewrite` 호출 없이 `False`
- update(repository.py:63-76): `found` 플래그가 False면 → `_rewrite` 호출 없이 `False`

즉 **실패 케이스에서는 디스크 쓰기가 0번** 일어납니다.

**한계도 같이 말할 것(가점 포인트)**: 전체를 메모리에 올려 다시 쓰므로 건수가 많아지면 비용이 O(n)입니다. 또 `os.replace` 직전 `f.flush()` + `os.fsync()`를 하지 않아 OS 버퍼에만 남은 상태에서 전원이 꺼지면 tmp가 비어 있을 수 있습니다. 완전한 내구성(durability)까지 원하면 fsync를 추가해야 합니다.

## 항목 3. 제너레이터 · 데코레이터 · 타입 힌트

### Q3-1. list/search를 제너레이터로 스트리밍 처리한 방식을 "어떻게" 구현했고, "왜" 유리한지 설명할 수 있는가?

**A. 어떻게** — `repository.py:21-28` `stream()`이 `return`이 아니라 `yield`를 씁니다.

```python
def stream(self) -> Iterator[Transaction]:
    with open(self.path, "r", encoding="utf-8") as f:
        for line in f:                          # 파일 객체 자체가 한 줄씩 주는 이터레이터
            line = line.strip()
            if not line:
                continue
            data = json.loads(line)
            yield Transaction.from_dict(data)   # 한 건 주고 그 자리에서 멈춤
```

`yield`가 있으면 이 함수는 호출해도 **바로 실행되지 않고 제너레이터 객체만 돌려줍니다.** 소비자가 한 건 달라고 할 때마다 멈췄던 지점부터 이어서 실행됩니다.

**소비자 3곳이 모두 이 스트림 위에 올라가 있습니다**

- `search()` (service.py:38) — `for tx in self.tx_repo.stream():` 조건 불일치는 `continue`로 버림
- `summary()` (service.py:79) — 해당 월이 아니면 `continue`, 누적 합계만 증가
- `list` — `cmd_list`(cli.py:24)가 `svc.search()` 결과를 슬라이스

**왜 유리한가 — 3가지**

1. **메모리**: 파일 전체를 리스트로 올리면 10만 건 × 객체 크기만큼 RAM을 먹지만, 스트리밍은 **동시에 살아 있는 객체가 1건**이라 파일이 커져도 메모리가 거의 일정합니다. (`json.load(전체)` 방식과의 결정적 차이)
2. **응답 시작 시각**: 첫 건을 얻기 위해 파일 끝까지 읽을 필요가 없습니다.
3. **`summary`는 결과를 아예 모으지 않습니다**: 합계·카테고리별 dict만 유지하므로(service.py:73-87) 거래 건수와 무관하게 메모리가 O(카테고리 수)입니다 — 스트리밍의 이점이 가장 순수하게 드러나는 지점.

**단, 정직하게 말할 부분**: `search()`는 마지막에 `result.sort(...)`로 최신순 정렬합니다(service.py:50). 정렬은 전부 모여야 가능하므로 **필터를 통과한 건수만큼은 메모리에 쌓입니다.** 즉 "읽기는 스트리밍, 정렬 대상은 결과 집합"이 정확한 표현입니다. 이걸 완전 스트리밍으로 만들려면 파일을 날짜 정렬로 유지하거나 `heapq.nlargest(limit, ...)`로 상위 N만 유지하면 됩니다.

### Q3-2. 데코레이터로 분리한 공통 기능이 무엇이며, "왜" 분리가 필요했는지 설명할 수 있는가?

**A.** `decorators.py`에 3개를 분리했습니다 — **로그 / 실행시간 측정 / 예외처리**. 셋 다 "업무 로직이 아닌데 여러 함수에 똑같이 반복되는 일"(횡단 관심사, cross-cutting concern)입니다.

| 데코레이터 | 하는 일 | 위치 |
| --- | --- | --- |
| `log_call` | 함수 시작/끝 로그 | decorators.py:32 |
| `timed` | `time.perf_counter()`로 ms 측정 | decorators.py:41 |
| `handle_errors` | `ValueError` / `FileNotFoundError`를 **[오류] + [힌트]** 로 변환 | decorators.py:51 |

**실제 적용**: `cli.py:185`의 `@handle_errors def main()` 딱 한 줄.

**왜 분리했나 — 데코레이터가 아니었다면 어땠을지로 답합니다**

CLI 명령 처리 함수는 10개(`cmd_add` ~ `cmd_import`)입니다. 사용자에게 스택트레이스를 보이지 않으려면 **10개 함수 전부에 try/except를 복붙**해야 합니다. 그러면

- 힌트 문구를 고칠 때 10곳을 고쳐야 하고,
- 새 명령을 추가할 때 try/except를 빠뜨리면 그 명령만 스택트레이스가 튀어나옵니다.

데코레이터는 `main()`이 모든 명령의 **단일 관문**이라는 구조를 이용해, 오류 처리 정책을 **한 곳에 한 번만** 적었습니다. `cmd_*` 함수들은 예외 처리 코드가 전혀 없어 업무 흐름만 읽힙니다.

**구현에서 짚을 포인트**

- `@functools.wraps(func)` (decorators.py:33) — 이게 없으면 포장된 함수의 `__name__`이 전부 `"wrapper"`가 되어 `log_call`이 찍는 함수 이름이 무의미해지고, 디버깅에서 원 함수를 식별할 수 없습니다.
- `*args, **kwargs`로 받기 때문에 **어떤 시그니처의 함수에도** 붙일 수 있습니다.
- 잡는 예외를 `Exception`이 아니라 `ValueError`/`FileNotFoundError`로 좁힌 이유: 예상 가능한 사용자 입력 오류만 친절하게 바꾸고, 예상 못 한 버그는 그대로 드러나야 고칠 수 있기 때문입니다.

### Q3-3. 타입 힌트를 적용해 얻는 이점을 실제 코드 예로 "어떻게" 확인했고 "왜" 도움이 되는지 설명할 수 있는가?

**A.** 타입 힌트를 **주석이 아니라 계약(contract)** 으로 썼습니다. 대표 3개로 설명합니다.

**① `def stream(self) -> Iterator[Transaction]:` (repository.py:21)**

반환형이 `list`가 아니라 `Iterator`라는 것 자체가 **"이건 한 번만 소비할 수 있고, `len()`을 쓸 수 없다"** 는 사용법을 알려줍니다. 만약 `list[Transaction]`이라고 적혀 있었다면 호출자가 `len(stream())`이나 두 번 순회를 시도했을 겁니다. 실제로 `delete()`(repository.py:56)는 두 번 봐야 해서 `list(self.stream())`으로 **의도적으로 물질화**했는데, 이 코드가 왜 필요한지도 타입이 설명해 줍니다.

**② `def get_budget(self, month: str) -> int | None:` (repository.py:158)**

**`| None`이 "예산이 없을 수 있다"는 사실을 코드가 강제로 말하게 합니다.** 이 힌트를 보고 호출자가 방어 코드를 쓴 게 실제로 남아 있습니다 —

- service.py:98 `if budget is not None and budget > 0:` (없으면 `usage_rate=None`)
- cli.py:40 `if s["budget"] is not None:` (없으면 예산 줄 자체를 출력 안 함)

`| None`이 없었다면 `total_expense / budget`에서 `TypeError: unsupported operand type(s) for /: 'int' and 'NoneType'`이 실행 시점에 터졌을 겁니다.

**③ `date_from: str | None = None, ... ) -> list[Transaction]` (service.py:34-36)**

검색 조건 6개가 전부 `| None`이라 **"안 준 조건은 필터하지 않는다"** 는 규칙이 시그니처만 봐도 읽힙니다. 실제 구현도 `if xxx is not None:` 형태로 그 계약을 그대로 지킵니다(service.py:39-48).

**"어떻게 확인했나"에 대한 답**

- **에디터**: `svc.summary(...)` 결과는 dict라 자동완성이 안 되지만, `tx.` 을 찍으면 `Transaction`의 필드(id/type/date/amount/category/memo/tags)가 바로 뜹니다. `models.py`의 `@dataclass` + 필드 타입 선언 덕분입니다.
- **정적 검사**: 실행하지 않고도 `mypy budget_app` 같은 도구로 "`int | None`을 `int` 자리에 넣었다"를 잡을 수 있습니다.
- **런타임 이점은 없음(중요)**: 파이썬은 힌트를 검사하지 않습니다. `amount: int` 자리에 문자열을 넣어도 파이썬은 통과시킵니다. 그래서 **런타임 검증은 `models.py:16-26` `__post_init__`에서 따로** 합니다 — `isinstance(self.amount, int)`, 양수 검사, `date.fromisoformat()` 형식 검사. **타입 힌트는 사람과 도구를 위한 문서, `__post_init__`은 데이터를 위한 문지기**로 역할을 나눈 것이 요점입니다.

## 항목 4. 설계 판단과 확장성

### Q4-1. JSONL과 CSV 중 선택한 저장 포맷의 장단점을 비교하고, "왜" 그 포맷을 택했는지 근거를 말할 수 있는가?

**A. 내부 저장은 JSONL, 외부 교환은 CSV — 용도를 나눴습니다.** 하나를 고른 게 아니라 **역할이 다르다**는 게 핵심 답변입니다.

| 기준 | **JSONL** (내부 저장 — 채택) | CSV (외부 교환용) |
| --- | --- | --- |
| 중첩 데이터 | `tags: ["meal","work"]` **배열 그대로** 저장 | 불가 → `"meal,work"` 문자열로 뭉개야 함 |
| 타입 | 숫자/문자/배열 구분 유지 (`15000` vs `"15000"`) | **전부 문자열**, 읽을 때마다 int 변환 |
| 필드 추가 | 줄마다 독립 객체라 **기존 줄 안 건드리고** 새 키 추가 가능 | 헤더 변경 = 전체 파일 재작성 |
| 한 줄 = 한 레코드 | ✅ append로 1건 추가, 스트리밍 읽기 가능 | ✅ (단 값 안에 쉼표·개행이 있으면 따옴표 규칙 필요) |
| 사람이 눈으로 보기 | 조금 장황 | 간결 |
| 엑셀/외부 도구 | 바로 안 열림 | ✅ 바로 열림 |

**택한 근거 3가지**

1. **`tags`가 리스트라서 결정적**입니다. CSV로 저장하면 `"meal,work"` → 읽을 때 다시 split → **값 안에 쉼표가 들어간 태그를 구분할 수 없는 손실**이 생깁니다. JSONL은 `json.loads` 한 번으로 원형 복구됩니다(repository.py:27-28).
2. **append-only 저장이 가능**합니다(repository.py:16-19). 거래 1건 추가에 파일 전체를 다시 쓰지 않고 끝에 한 줄만 붙입니다. 일반 JSON(파일 전체가 배열 하나)이었다면 **1건 추가에도 전체 파싱 → 전체 재작성**이 필요했을 겁니다. JSONL은 **JSON의 표현력 + 줄 단위 append**를 동시에 가집니다.
3. **줄 단위라 스트리밍과 궁합이 맞습니다.** `for line in f:` → `json.loads(line)` 구조가 그대로 제너레이터가 됩니다(Q3-1).

**그러면 CSV는 왜 남겼나**: 사용자가 엑셀로 열고 남에게 주는 용도(`export`/`import`)는 **호환성이 최우선**이라 CSV가 맞습니다. 즉 **저장 포맷(JSONL)과 교환 포맷(CSV)을 분리**하고, 그 변환 책임을 `service.py:129-170`에 몰아뒀습니다.

**JSONL의 단점도 인정할 것**: ① 부분 수정이 안 돼서 update/delete가 전체 재작성입니다(Q2-3). ② 인덱스가 없어 id 조회가 O(n)입니다. ③ 필드명이 줄마다 반복돼 파일 크기가 CSV보다 큽니다. 이 셋이 다음 질문의 병목과 직결됩니다.

### Q4-2. 거래가 10만 건으로 늘어난다면, 현재 구조에서 병목이 어디이며 "어떻게" 개선할지 설명할 수 있는가?

**A. 병목은 4곳이고, 가장 아픈 건 `next_id()`입니다.** 순서대로 말씀드립니다.

**① `next_id()` — 거래 1건 추가마다 10만 줄 전수 스캔 (최우선)**

`repository.py:32-40`은 파일 전체를 스트리밍하며 최대 번호를 찾습니다. 즉 **add 1회 = 전체 파일 1회 읽기(O(n))**.

더 나쁜 건 `import_csv`입니다. `service.py:159`가 행마다 `add_transaction()`을 부르고, 그게 매번 `next_id()`를 부르므로 **CSV m행 import = 파일 전체 m번 읽기 = O(n×m)** 이 됩니다.

- **개선**: (a) 마지막 id를 `data/meta.json`에 저장해 O(1)로 읽기, 또는 (b) 파일 끝 한 줄만 읽어 채번(append-only라 마지막 줄이 최대값), 또는 (c) import는 시작할 때 한 번만 채번하고 메모리에서 +1씩 증가.

**② `add_transaction()`의 카테고리 검증 — 매번 카테고리 파일 재읽기**

`cat_store.exists()`(repository.py:107) → `list_all()`이 매번 파일을 다시 엽니다. 카테고리 파일은 작지만 **import 만 행이면 만 번 open** 합니다.

- **개선**: 생성자에서 한 번 읽어 `set`으로 캐시. `in set`은 O(1).

**③ `update` / `delete` — 1건 고치려고 10만 건 전부 메모리에 올리고 전부 다시 쓰기**

`repository.py:56, 64`의 `list(self.stream())`이 스트리밍의 이점을 여기서만 포기합니다.

- **개선(파일 유지)**: `list()`로 모으지 말고 **읽으면서 바로 tmp에 흘려 쓰기** — 메모리 O(1), 디스크 쓰기는 여전히 O(n)이지만 RAM 문제는 사라집니다.
- **개선(근본)**: 삭제를 즉시 반영하지 않고 tombstone(삭제 표시)만 append 해두고, 주기적으로 compaction. 쓰기가 O(1)이 됩니다.

**④ `search()`의 정렬 및 `list`의 낭비**

- `search()`는 조건에 맞는 걸 전부 `result`에 모은 뒤 정렬(service.py:49-50) → 조건이 넓으면 10만 건이 메모리에 올라옵니다.
- 특히 `cmd_list`(cli.py:24)는 `svc.search()[:args.limit]` — **10만 건을 전부 읽고 전부 정렬한 뒤 10건만 씁니다.**
- **개선**: `limit`을 서비스까지 내려보내고 `heapq.nlargest(limit, stream, key=...)` 사용 → 메모리 O(limit). 또는 파일이 날짜 오름차순이라는 성질을 이용해 뒤에서부터 읽기.

**⑤ 근본적 한계 — 조회 조건 하나에 항상 전체 스캔**

인덱스가 없어 `--category food`도 10만 줄을 다 봅니다. 규모가 더 커지면 **SQLite로 전환**하는 게 정답입니다. 표준 라이브러리(`sqlite3`)이고, 날짜·카테고리에 인덱스를 걸면 조회가 O(log n)이 되며, update/delete가 전체 재작성 없이 끝나고 트랜잭션까지 공짜로 얻습니다.

**그리고 그 전환 비용이 작다는 게 이 설계의 성과입니다** — 파일 I/O가 `repository.py` 안에만 갇혀 있으므로 **`SqliteTransactionRepository`를 새로 만들어 갈아끼우면 `service.py`·`cli.py`는 한 줄도 안 바뀝니다.**

### Q4-3. import CSV에 일부 깨진 행이 섞이면, "어떻게" 처리해 사용자 신뢰를 지킬지(부분 성공/롤백/리포트) 설명할 수 있는가?

**A. 현재 구현은 "부분 성공(partial success) + 건수 리포트" 전략입니다.** 깨진 행에서 멈추지 않고 건너뛴 뒤, 마지막에 결과를 보고합니다.

`service.py:150-170`:

```python
for row in reader:
    try:
        ... self.add_transaction(...)
        imported += 1
    except (ValueError, KeyError):
        skipped += 1
return {"imported": imported, "skipped": skipped}
```

`cli.py:116` → `[완료] imported=5, skipped=2`

**어떤 행이 걸러지나** — 검증이 이미 3중으로 걸려 있어 별도 코드가 필요 없습니다.

| 깨진 유형 | 어디서 잡히나 | 예외 |
| --- | --- | --- |
| 날짜 형식 오류 `2024-13-99` | models.py:22 `date.fromisoformat()` | ValueError |
| 음수/0 금액, 숫자가 아닌 금액 | models.py:19 / `int(row["amount"])` | ValueError |
| `type`이 income/expense가 아님 | models.py:17 | ValueError |
| 미등록 카테고리 | service.py:15 | ValueError |
| 헤더에 컬럼 자체가 없음 | `row["type"]` | KeyError |

**왜 부분 성공을 택했나 — 3가지 전략 비교**

| 전략 | 동작 | 장점 | 단점 |
| --- | --- | --- | --- |
| ① 첫 오류에서 중단 | 1행 깨지면 전체 실패 | 단순 | 1만 행 중 1행 때문에 전부 못 넣음 |
| ② **부분 성공(채택)** | 정상만 넣고 나머지 skip | 대량 데이터에 현실적 | **어느 행이 왜 빠졌는지 모르면 신뢰가 깨짐** |
| ③ 전부-아니면-전무(롤백) | 하나라도 깨지면 원상복구 | 일관성 최고 | 사용자가 한 행 고치려고 전체를 다시 import |

가계부처럼 **행끼리 서로 의존하지 않는(독립 레코드)** 데이터는 ②가 맞습니다. 은행 이체처럼 행끼리 묶여야 하는 데이터라면 ③이어야 합니다. **선택 기준은 "레코드 간 원자성이 업무적으로 필요한가"** 입니다.

**현재 구현의 약점과 개선안(이걸 같이 말해야 만점)**

현재는 `skipped=2`라는 **숫자만** 알려주고, **몇 번째 행이 왜 빠졌는지 알려주지 않습니다.** 그러면 사용자가 원본 CSV를 직접 뒤져야 해서 오히려 신뢰가 떨어집니다. 개선 방향:

1. **행 번호 + 사유 수집**: `for i, row in enumerate(reader, start=2)` (헤더가 1행)로 행 번호를 잡고, `except ... as e:` 에서 `errors.append((i, str(e)))` → 마지막에 `3행: amount는 양의 정수여야 합니다` 형태로 최대 N건 출력.
2. **실패분 재활용 파일**: 실패한 행만 `import_failed.csv`로 다시 써 주면, 사용자가 그 파일만 고쳐서 재실행하면 됩니다. (**부분 성공의 신뢰는 "남은 일을 어떻게 끝내는지"까지 알려줄 때 완성됩니다.**)
3. **`--dry-run` 옵션**: 저장하지 않고 검증만 해서 몇 건이 통과/실패인지 미리 보여주기.
4. **중복 방지**: 같은 CSV를 두 번 import 하면 지금은 그대로 2배가 됩니다. (date+type+amount+category) 해시로 중복을 skip 하거나, 최소한 경고해야 합니다.
5. **롤백이 필요하다면**: 지금 구조에서도 어렵지 않습니다. 전 행을 먼저 `Transaction` 객체로 다 만들어 검증하고(1단계), 하나라도 실패하면 저장 없이 종료, 전부 통과했을 때만 append(2단계) — **검증과 저장을 분리**하면 됩니다.

## 부록. 미리 알고 있어야 할 현재 코드의 결함 (항목 1 FAIL 관련)

질문받기 전에 알고 있으면 "왜 FAIL인지 알고 있고, 원인도 안다"는 인상을 줍니다.

1. **`update`가 항상 실패합니다 — 들여쓰기 버그** (`cli.py:56-69`)
   `if not fields:` 이하 전체가 `for` 루프 **안**에 들어가 있습니다. 첫 번째 키인 `date`가 `None`이면 그 시점의 `fields`는 비어 있으므로, `--amount`만 준 정상 명령도 `[안내] 수정할 항목을...` + `exit(1)`로 끝납니다.
   → **`if not fields:` 부터를 for 루프 밖으로 내보내면** 해결됩니다.

2. **오류가 나도 종료 코드가 0입니다** (`decorators.py:51-62` + `__main__.py:12`)
   `handle_errors`가 예외를 잡고 **아무것도 반환하지 않아 `None`** 이 됩니다. `sys.exit(main())` → `sys.exit(None)` → **종료 코드 0**. "오류 시 0이 아님" 요건과 충돌합니다.
   → `except` 블록 끝에 `return 1` 추가.

3. **`--q`(메모 키워드) 옵션이 동작하지 않습니다** (`service.py:34-51`)
   `q` 파라미터를 받기만 하고 필터 조건이 없습니다.
   → `if q is not None and q not in tx.memo: continue` 한 줄 추가.

4. **export `--month`의 마지막 날이 `-31` 고정** (`service.py:133`)
   문자열 비교라 2월도 결과는 맞지만, 존재하지 않는 날짜라 의미상 부정확합니다. → `calendar.monthrange()` 사용 권장.

5. **`repository.py:3`에 `from multiprocessing import Value` 미사용 import** — 삭제 대상.

6. **출력 문구 오타** — `cli.py:49` `[ 삭제완료]`(공백), `cli.py:93` `[저장완료]`, `cli.py:95` `[안네]이미 있는 카데고리`. README 표기와 불일치합니다.
